- **P1 (now):** needed before the first feature slice is built, or expensive to change later.
- **P2 (first slice):** needed while building the onboarding slice.
- **P3 (later):** needed before production or when the relevant module starts.

## Delivery and process

### R-01 Define a small Release 1 scope and build it end to end · P1
- **Gap:** The current plan finishes discovery for all 117 subprocesses before building. No running code has yet tested any of the 263 rules.
- **Recommendation:** Fix Release 1 as a "walking skeleton" through the real architecture:
  1. Platform staff sign in.
  2. A Registration Officer captures a registration, including offline.
  3. It is verified, independently reviewed and decided.
  4. The Company is established with a generated code.
  5. The first Company Administrator is invited and signs in, and sees only their company.

  Include minimal G1 (assignment), G4 (notification) and G5 (independent review). Exclude appeals, reconsideration, subscriptions and everything from BP-02 onward.
- **Why:** It tests the hardest architectural decisions early (offline sync, tenant isolation, authorisation, audit, state machines) on a small scope, and gives stakeholders something to react to.
- **Alternative:** Finish analysis first. That costs months of unvalidated rules, and design problems surface late.

## Backend architecture

### R-05 Package by module; enforce boundaries automatically · P1
- **Gap:** The plan requires module boundaries, but nothing stops one module from calling another module's repositories directly. In a monolith, that erosion is the main risk.
- **Recommendation:**
  - Organise packages as `com.transithub.<module>`, where `<module>` is `onboarding`, `identity`, `governance`, `shared` and later one per business process. Inside each module use `api` (controllers, DTOs), `application` (use-case services, transactions), `domain` (aggregates, rules) and `infrastructure` (persistence, adapters).
  - Each module exposes a small public API (a facade interface plus events). Everything else stays package-private or `internal`.
  - Enforce this with **Spring Modulith**, using its module verification test and event publication registry (verify the version that supports Boot 4.2 when adopting), or with **ArchUnit** rules if Modulith doesn't fit.
  - Rename the current `company` module to `onboarding`. Company and CompanyRegistration both belong to BP-01.01.
- **Why:** Boundaries break the build instead of being left to code review. It also leaves a clean path to extract a service later.
- **Decision:** ______ **Notes:**

### R-06 Tenant isolation: shared schema + `company_id` + PostgreSQL row-level security · P1
- **Gap:** Isolation is a top principle, but there is no mechanism for it yet.
- **Recommendation:** Defence in depth:
  1. **One schema, with `company_id NOT NULL` on every tenant-owned table.** Composite foreign keys include `company_id`, so a row can't reference another company's row.
  2. **The application** resolves the tenant only from the authenticated user (never from a request parameter) into a `TenantContext`. Repositories filter by it, for example with Hibernate's tenant-discriminator support or an explicit query convention.
  3. **PostgreSQL row-level security (RLS)** policies on tenant tables use `current_setting('app.company_id')`, set per transaction. A bug in step 2 then returns zero rows instead of leaking another company's data.
  4. **Platform staff** access across companies through explicit, audited platform roles (break-glass access per BR-ONB-094), not by switching RLS off.
- **Why not schema- or database-per-tenant:** with many small transport companies, migrations, connection pools and cross-tenant reporting become expensive. A shared schema with RLS is the standard choice for this scale.
- **Decision:** ______ **Notes:**

### R-07 Use an external identity provider (Keycloak); keep authorisation in TransitHub · P1
- **Gap:** Phase 3 lists authentication, but there is no decision on how. Building password storage, MFA, reset flows and session management yourself is high-risk work with no business value.
- **Recommendation:**
  - **Keycloak** (open source, self-hosted, OpenID Connect) handles authentication: login, MFA, password policy, account recovery, and long-lived tokens for field devices.
  - The backend is a Spring Security **resource server**.
  - **Authorisation stays in TransitHub's database:** which roles a user has, in which company or branch, plus delegations and separation of duties. Those are business rules, not identity-provider configuration.
  - Map Keycloak user → `UserAccount` (TransitHub) → optionally `Employee`. This keeps the approved rule that employees are separate from login accounts.
- **Alternatives:** Auth0 or Okta (managed, cost per user, data residency to consider); building authentication yourself (not recommended).
- **Decision:** ______ **Notes:**

### R-08 Permission-based, scoped authorisation, with separation-of-duties checks in the application layer · P1
- **Recommendation:**
  - Fine-grained **permissions** (`registration.verify`, `registration.decide`, `correctiveAction.reopen.approve`) are grouped into roles. Role assignments are scoped to the platform, a company or a branch, and have validity periods.
  - Checks happen in **application services**, not only on controllers. Rules that depend on data, such as "approver ≠ verifier of *this* registration" (BR-ONB-046/062), need the loaded aggregate, so they are domain checks.
  - Every denial is audited.
  - A job title or position never maps to a permission automatically (approved rule).
- **Decision:** ______ **Notes:**

### R-09 Time-ordered UUIDs (v7) generated by the application; separate human-readable references · P1
- **Gap:** Offline devices must create records before the server knows about them. Random UUIDs (v4) work but fragment indexes.
- **Recommendation:**
  - Primary keys are **UUIDv7**, created by the application or the device. They are unique offline and time-ordered, which keeps indexes efficient. Generate them with Hibernate's v7 UUID generator or a small library; confirm in the first slice.
  - **Human-readable references** are separate columns with their own rules:
    - **Registration reference:** generated on the device and unique offline, for example `REG-<officerCode>-<yyMMdd>-<seq>`.
    - **Company code:** generated by the server on approval (R-16).
  - The registration UUID doubles as the **sync idempotency key**.
- **Decision:** ______ **Notes:**

### R-10 Explicit state machines inside aggregates; commands, not status updates · P1
- **Recommendation:**
  - Each lifecycle (registration, trip, booking, parcel, corrective action) is a status enum plus **domain methods** such as `submit()`, `requestInformation()` and `decide()`. Each method checks the allowed transition and the preconditions, records a status-history row and raises a domain event.
  - There is no generic `setStatus()` and no `PATCH status` API.
  - Don't use a state-machine framework such as Spring Statemachine. Plain code is simpler to read, test and debug at this size.
- **Why:** Most of the approved rules are of the form "X may only happen when Y". This puts each such rule in exactly one testable place.
- **Decision:** ______ **Notes:**

### R-11 Optimistic locking on every aggregate; idempotency keys on create / money endpoints · P1
- **Recommendation:**
  - Put an `@Version` column on every aggregate root. Two approvers deciding at once means one gets a 409 Conflict rather than both succeeding.
  - Add an `Idempotency-Key` header to every endpoint that creates something or moves money (registrations, sync, bookings, payments, refunds, parcel acceptance, promotion redemption). The key and response are stored in an `idempotency_record` table, so retries replay the original response. This implements the idempotency list in your plan §10.4.
- **Decision:** ______ **Notes:**

### R-12 Domain audit events + status-history tables, written in the same transaction · P1
- **Recommendation:**
  - **Status history per aggregate**, for example `registration_status_change`. This is business data the UI shows.
  - **One append-only `audit_event` table** holding actor, action, entity, company, a summary of what changed, reason and correlation ID. It is written by application services in the same transaction as the change. Block `UPDATE` and `DELETE` with database permissions or triggers.
  - Corrections create revisions (`RegistrationRevision`) rather than overwriting.
  - Avoid generic row-level auditing such as Hibernate Envers as the main audit trail. It records which columns changed, not *why* or *which business action*, and the rules need the business action.
- **Decision:** ______ **Notes:**

### R-13 Transactional outbox for module events · P2
- **Recommendation:**
  - Domain events (for example `CompanyEstablished`) are written to an outbox in the same transaction as the change and delivered after commit. Consumers are idempotent.
  - Spring Modulith's event publication registry provides this inside the monolith (if R-05 adopts Modulith); otherwise use a simple `outbox_event` table with a scheduled publisher.
  - Externalise to a message broker only when a real need appears.
- **Decision:** ______ **Notes:**


### R-14 API standards: commands as sub-resources, ProblemDetail with codes, OpenAPI · P2
- **Recommendation:**
  - **Resources** are nouns (`/api/v1/registrations`). **State transitions** are explicit commands: `POST /registrations/{id}/submit`, `/information-requests`, `/decision`.
  - Errors use ProblemDetail (already in place) plus a stable machine-readable `code`, for example `REGISTRATION_NOT_ACKNOWLEDGED`, so the UI and tests don't depend on message text.
  - Cursor or page pagination on all lists.
  - ISO-8601 UTC timestamps.
  - OpenAPI generated with springdoc and checked in CI.
  - The version stays in the path (`/v1`).
- **Decision:** ______ **Notes:**

### R-15 Typed, versioned, per-company policy settings, not a rules engine · P2
- **Gap:** Part F details (deadlines, retry counts, escalation levels, allowances) must be configurable per company, per your approved principle.
- **Recommendation:**
  - Store a `policy_setting` table keyed by (scope = platform / company, key, version, value as JSON, effective from, approved by).
  - Read settings through **typed Java policy classes**, for example `VerificationPolicy.deadline()`.
  - Platform defaults apply until a company overrides them, where the rules allow.
  - Changes are versioned and audited, and each record stores which policy version applied to it.
- **Why not a rules engine (Drools etc.):** it hides rules from code review and tests, and your rules are workflows with parameters, not complex inference.
- **Decision:** ______ **Notes:**

### R-16 Company-code generation from a PostgreSQL sequence · P2
- **Recommendation:**
  - Generate the code inside the approval transaction from a dedicated PostgreSQL sequence.
  - Proposed format: `TH` + 6 digits + 1 check digit, for example `TH0000127`. The check digit catches typing errors.
  - Codes are never reused and never change, including on ownership transfer (BP-01.09).
  - Drop `companyCode` from the create request once the registration flow replaces the temporary endpoint.
- **Decision:** ______ (format to approve) **Notes:**

### R-17 Evidence files in S3-compatible object storage · P2
- **Recommendation:**
  - File bytes go to object storage: MinIO locally, any S3-compatible service in production. Metadata and checksums go in PostgreSQL (`stored_document`).
  - Upload and download through short-lived pre-signed URLs, checked against permissions.
  - Validate content type and size, scan for malware before a file is accepted, and encrypt at rest.
  - Retention classes per BR-ONB-098.

### R-18 Money as `BigDecimal` / `NUMERIC` + currency; clear time-zone rules · P2
- **Recommendation:**
  - Money uses a `Money(BigDecimal amount, Currency currency)` value object stored as `NUMERIC(19,4)` plus an ISO currency code. Never use `double`.
  - Instants are stored as `TIMESTAMPTZ` in UTC.
  - Each company and branch has a time zone. Service dates and timetable times are local (`LocalDate` / `LocalTime` + zone).
  - Deadlines ("2 working days") need a working-calendar service, which ties into R-15.

  - Seat holds expire (for example after 10 minutes, set by policy).
  - Never rely on "check then insert" in Java.

## Frontend

### R-23 Separate the three audiences into apps in one frontend monorepo · P1
- **Gap:** The plan says "React frontend" but serves three very different audiences.
- **Recommendation:** One repository `transithub-frontend` using pnpm workspaces:

  | App | Users | Notes |
  |---|---|---|
  | `apps/backoffice` | Platform staff + company staff | Vite SPA (React + TS, approved). Menus driven by role and permission. |

  | `apps/marketplace` (later) | Passengers, parcel senders | Public and search-engine-visible, so needs server-side rendering, for example React Router framework mode or Next.js. Not in Release 1. |

  Shared packages: `ui` (design system), `api-client` (generated from OpenAPI), `i18n`, `auth`.
- **Why:** Different security, offline and search-engine needs, plus shared components and API types.
- **Decision:** ______ **Notes:**

### R-24 Offline field registration: PWA first, validated by a device spike · P1
- **Gap:** Offline capture is an approved, day-one requirement (BR-ONB-021–029) and the riskiest frontend feature. No client technology has been chosen.
- **Recommendation:**
  - Build `apps/field` as an installable **Progressive Web App**: service worker, IndexedDB via Dexie for drafts and evidence, and a sync queue that retries using the registration UUID as the idempotency key.
  - Encrypt local data with WebCrypto, using a key unlocked by the officer's PIN, to meet BR-ONB-029. Request persistent storage. Purge local copies after the server confirms sync (subject to retention).
  - **Run a 1–2 week spike first** on your actual field devices. Test: storage persists across days offline; camera capture of documents works; encryption performance is acceptable; and a ~20 MB evidence upload succeeds on weak networks.
  - **If the spike fails** (for example the browser clears storage, or the devices are not managed), switch `apps/field` to **React Native (Expo)** with encrypted SQLite. Most TypeScript skills and API types carry over.
- **Decision needed from you:** which devices officers use (Android phones or tablets? company-managed?).
- **Decision:** ______ **Notes:**

### R-25 Frontend stack: TanStack Query, React Router, React Hook Form + Zod, Mantine, generated API client · P2
- **Recommendation:**
  - **Server state:** TanStack Query, with caching, retries and offline mutation support. Don't build a global Redux store for server data.

  - **Testing:** Vitest + Testing Library for components; Playwright for end-to-end tests of whole use cases.

### R-26 Server tells the UI which actions are allowed (`allowedActions`) · P2
- **Gap:** Rules such as "only an independent approver may decide, and only when Recommended" would otherwise be duplicated in React, and would drift from the backend.
- **Recommendation:** Every aggregate response includes `allowedActions` (for example `["requestInformation", "recordRecommendation"]`), computed by the backend from state plus the current user's permissions and separation of duties. The UI shows and hides buttons from this list and enforces nothing itself. The backend still re-checks on every command.
- **Why:** Keeps your rule that critical business rules are enforced by the backend, and keeps the UI simple.
- **Decision:** ______ **Notes:**

### R-27 Back-office authentication via a backend-for-frontend (cookie session) · P2
- **Recommendation:**
  - The back-office signs in through the backend using OIDC with Keycloak.
  - The backend holds the tokens and gives the browser an `HttpOnly`, `Secure`, `SameSite` session cookie, with CSRF protection.
  - No access tokens are kept in browser JavaScript. This is the current best practice for browser apps that handle sensitive data.
  - The field app (R-24) uses tokens with offline refresh, because it must work while offline.
- **Decision:** ______ **Notes:**

### R-28 A unified "My Work" inbox as the core back-office screen · P2
- **Gap:** Most approved rules create work for someone: verify, review, acknowledge, accept or refuse, escalate, reopen. Without one place to see it, deadlines will be missed and escalation rules will fire constantly.

  - Overdue items, with deadline countdowns.
  - Filters by module.

  Every work item opens its detail page with its `allowedActions`. Build it in Release 1 with registration work items only.

## Passenger side: booking, ticketing and the marketplace

**Why this section exists:** the earlier register mentioned passengers only in passing (R-20 seats, R-21 payments, R-23 marketplace app). Ticket sales bring in the commission revenue and generate the most traffic, and they raise the hardest concurrency and payment problems.

**Updated 26 Nov 2026:** BP-03 already has approved decisions (A–I), recorded in [bp-03-passenger-booking-register.md](../requirements/bp-03-passenger-booking-register.md). The recommendations below are consistent with them and **implement** them. Where they go further, they are engineering proposals for the 15 discovery topics, not approved rules.

### R-35 Complete BP-03 discovery now, in parallel with the onboarding build · P1
- **Gap:** BP-03 has ten subprocesses and nine approved decision areas (A–I), but no numbered rules. Fifteen topics are still open, among them reservation expiry, failed payments, refunds, offline sales and boarding.
- **Recommendation:**
  - Turn the approved decisions into numbered rules with official IDs (proposed `BR-BKG-nnn`), assigned on confirmation, never back-dated.
  - Resolve the 15 discovery topics, using R-36 to R-44 as starting proposals.
  - Keep governance rules out: they reuse G1–G9 ([04-business-rules-analysis.md](../analysis/04-business-rules-analysis.md)).
- **Why:** The open topics decide the data model and the payment flow. Discovery takes weeks, so it should happen while Release 1 is being built, not after.
- **Decision:** ______ **Notes:**

### R-36 Release the passenger side in two steps: ticket office first, marketplace second · P1
- **Gap:** "Booking and ticketing" covers two very different products.
- **Recommendation:**
  - **Release 2, first ticket sold at a ticket office.** A company ticketing agent sells a seat on a timetabled trip, takes cash or mobile money, and issues an SMS/printed ticket. The conductor checks it at boarding. There is no commission and no public site, and every user is a signed-in member of staff.
  - **Release 3, the public marketplace.** Passengers search across companies, pay online and receive an e-ticket. TransitHub records commission.
  - Both use the **same** booking, seat-inventory and payment core. The marketplace is a new channel, not a second booking system.
- **Why:** The ticket office proves seat inventory, fares, payment and boarding with a small number of trusted users. The marketplace then adds public scale, fraud risk and commission on top of a core that already works.
- **Alternative:** marketplace first, to start earning commission sooner. This carries more risk, because public traffic would hit an untested core.
- **Decision:** ______ **Notes:**

### R-37 Passenger accounts in a separate identity realm; also allow guest booking by phone number · P2
- **Gap:** Passenger accounts are approved (BP-03.01) and must be separate from employee accounts (decision A). Whether a passenger can book **without** an account is not decided.
- **Recommendation:**
  - Passenger accounts live in their **own Keycloak realm** (R-07), never the staff realm, so a passenger login can never reach staff functions. This implements decision A.
  - **Proposed (needs your decision):** also allow guest booking with name and phone number. "My bookings" for guests uses a one-time SMS code. Ticket-office passengers are usually guests.
  - Collect an ID number only when a company policy or regulator requires it (discovery topic 9).
  - Passenger data is personal data under Zambia's Data Protection Act 2021. Collect the minimum, state retention periods, and record marketing consent separately.
- **Why:** The phone number is how passengers pay (mobile money) and receive tickets (SMS). Forcing registration at the ticket office or on a first online purchase loses sales.
- **Decision:** ______ **Notes:**

### R-38 Booking only confirmed when payment is confirmed; design for slow, asynchronous mobile money · P1
- **Gap:** Mobile money is not instant. The passenger receives a prompt on their phone and approves it with a PIN, sometimes minutes later, and sometimes the confirmation callback arrives late or never.
- **Recommendation:**
  - The flow is **Reservation → PendingPayment → Confirmed**, and the ticket is issued **only** on confirmed payment from BP-09. This implements approved decisions C, D and F ([03-domain-model.md](../analysis/03-domain-model.md) §3.10). The timings and failure handling below are proposals for discovery topics 1–3.
  - The hold time is a per-company policy (R-15). It must be long enough for a mobile-money prompt, and it is extended once a payment request is in flight.
  - **Late success:** if payment succeeds after the hold expired, re-seat the passenger if the seat is still free. Otherwise refund automatically and notify them. Never leave money without a booking.
  - **No callback:** if the provider doesn't call back, BP-09 polls the provider's status, then reconciles daily (R-21).
  - Every step uses idempotency keys (R-11). A double-tap or retry never charges twice.
- **Why:** This is the most common source of disputes in African bus ticketing: "I paid but got no ticket". It has to be designed in, not patched later.
- **Decision:** ______ **Notes:**

### R-39 Tickets as signed QR codes plus SMS; boarding checks work offline · P2
- **Gap:** The ticket format and the boarding check are not defined (discovery topics 10–11). Ownership is approved: BP-03 validates tickets and BP-04 does boarding.
- **Recommendation:**
  - **Ticket:** a QR code holding a **digitally signed** booking reference, plus an SMS with a short human-readable code, for passengers without smartphones. A printed ticket at the office uses the same QR code.
  - **Boarding:** the conductor's device downloads the trip manifest before departure and checks tickets **offline**, by checking the signature and the manifest. Results sync later, which reuses the offline patterns in R-24.
  - **Ownership** (approved): BP-03 issues and validates tickets. BP-04 owns the manifest and the boarding record.
- **Why:** A forged or reused screenshot must fail the check. Bus stations and roadside stops often have no signal.
- **Decision:** ______ **Notes:**

### R-40 Marketplace is a platform-level, cross-company read model; bookings still belong to the company · P1
- **Gap:** The marketplace is the one place where data from **many** companies is shown together, which collides with strict tenant isolation (R-06).
- **Recommendation:**
  - Companies **publish** trips, fares and availability to a platform-owned `marketplace` read model. It holds public data only, fed by events (R-13, R-22). Public search never queries tenant tables directly.
  - A marketplace booking is still a **company** booking in BP-03, under that company's `company_id`. TransitHub holds a separate marketplace **order** with the passenger contact, the channel and the commission.
  - A company sees only its own passengers. A booking that spans two companies (a connection) is **not** supported at first.
- **Why:** This keeps tenant isolation intact and gives a clean record of what TransitHub earned. Search also stays fast under public load.
- **Decision:** ______ **Notes:**

### R-41 Record the sales channel on every booking; commission calculated by BP-09 from a rate snapshot · P1
- **Gap:** The revenue model is approved ("commission on marketplace sales, none at the ticket office"), but how commission is calculated and collected is not.
- **Recommendation:**
  - Every booking records its **channel** (approved decisions E and I): `COMPANY_OFFICE`, `AUTHORISED_AGENT` or `MARKETPLACE_ONLINE`, plus later channels.
  - When a marketplace booking is confirmed, BP-09, which owns commission accounting (approved boundary), calculates commission from the company's **commercial agreement** (BP-01.04) and stores the rate used, so later rate changes don't alter history.
  - Cancellations and refunds reverse commission according to a stated rule.
  - **Merchant of record** is a business decision (see the decisions below). The usual options are:
    - TransitHub collects online payments and settles to companies **minus commission**. This makes commission easy to collect, but TransitHub holds customer money and may need a payment licence or a regulated partner.
    - Each company is paid directly into its own merchant account, and TransitHub **invoices commission**. This is simpler to regulate, but commission is harder to collect.
- **Why:** Commission is a core revenue stream. It needs to be correct from the first marketplace sale and auditable afterwards.
- **Decision:** ______ **Notes:**

### R-42 Fares owned by BP-03 as versioned fare tables · P2
- **Gap:** Open question 1: who owns fares?
- **Recommendation:**
  - BP-03 owns a **fare table** per company, route and origin–destination pair (if segment selling is allowed). Fares can vary by class or seat type and by passenger type (adult, child), with effective-from and effective-to dates and approval before publication.
  - BP-02 owns routes and stops. BP-09 records the money but doesn't set prices.
  - The booking stores the **fare actually charged**, so later fare changes never alter past tickets.
  - Promotions and discounts are a separate, auditable adjustment, not an edit to the fare.
- **Why:** Fares change often and need history and approval. Putting them in routes or finance mixes up who owns what.
- **Decision:** ______ **Notes:**

### R-43 Channels for passengers without smartphones or data · P3
- **Gap:** Many passengers use feature phones or have limited data.
- **Recommendation:**
  - The ticket office and SMS tickets cover this from Release 2.
  - **USSD booking** (dialling a short code) through a USSD aggregator is a strong later channel. Plan for it by keeping booking logic behind channel-neutral application services, so USSD is just another adapter.
  - WhatsApp booking is a possible later option.
  - Commission rules per channel are decided under R-41.
- **Why:** Reaching passengers who aren't online widens the marketplace. Building the core channel-neutral now costs almost nothing.
- **Decision:** ______ **Notes:**

### R-44 Ticket offices keep selling when the connection drops · P2
- **Gap:** Bus-station ticket offices may lose connectivity. Offline sales risk selling the same seat twice.
- **Recommendation:**
  - **Release 2 default:** online-only sales, with clear "offline" messaging, a fall-back to manual receipts, and later controlled back-capture.
  - **Later, if needed:** an office reserves a **block of seats** per trip while online and sells only from that block offline, syncing afterwards. This is the only safe way to sell offline without double-selling.
- **Why:** Offline sales are a real need, but "offline with no allocation" means double-selling. Decide the policy before building.
- **Decision depends on:** how reliable ticket-office connectivity is (see the decisions below).
